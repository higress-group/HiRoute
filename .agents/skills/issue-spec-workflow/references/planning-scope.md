# Requirement scope and verification ownership

Before authoring Proposal SPECs, inspect current code, applicable durable specs and representative tests. Summarize the existing capability, what can be reused, the actual gap or changed behavior, and inherited constraints in the Proposal's existing sections, with repository references. Distinguish observed implementation from intended contracts; do not present unverified assumptions as working capabilities. This is authoring context, not a new artifact or approval step.

Each Proposal SPEC defines a new, changed or corrected observable product contract within the confirmed scope. Explain what must become possible or behave differently on top of that baseline. A new consumer or integration boundary can need a SPEC even when its underlying engine is reused. Keep unchanged capabilities as baseline and inherited contracts as constraints; do not restate them as separate new deliverables unless the change modifies or newly exposes that contract.

WHEN/THEN scenarios describe product inputs, states, outcomes and meaningful failure behavior. They remain precise enough to reject an incorrect implementation, without prescribing private helpers or a test procedure. Platforms and environments belong in SPEC only when they define supported product behavior, not merely where a check happens to run.

Design explains the implementation and overall verification strategy. Its TASKs carry concrete verification work: relevant cases, environment or platform matrix, commands or test entry points, and expected results/evidence. Put this in a Verification subsection of the TASK summary or actionable checklist items while preserving canonical TASK fields. A dedicated integration-validation TASK is useful only when it is a coherent work unit; link it to the actual SPECs it verifies rather than inventing a validation-only SPEC for coverage. If existing behavior only needs evidence, keep that work in the selected Design/TASK or simple Issue; it does not create a new product requirement. A Proposal-only request does not require creating Design or TASK early.

For changes to a user-facing critical path, describe in the existing Design/TASK when the user can proceed, which dependencies must be resolved first, and what bounds the synchronous work. Keep unrelated history and optional maintenance outside that path; justify any unavoidable full scan.

Keep the affected contract self-contained: change scope is incremental, but an implementer must not reconstruct intended behavior from a patch description. Repository durable specs describe the complete current contract after the change, including still-applicable behavior; do not replace them with delta-only notes.

For example, when an existing router gains a headless client, SPEC can require that client's CLI configuration and task-based routing through the existing engine. Existing routing algorithms are baseline unless changed. Running a Linux tool-call journey and collecting the selected-model evidence belongs in a Design TASK; adding Linux as a newly supported product platform would itself be a requirement.
