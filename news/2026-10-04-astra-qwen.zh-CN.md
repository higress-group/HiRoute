# HiRoute 智能路由实战：GPT-6 Astra × Qwen-3.8 Flash，同等质量下成本降低 90%

一次软件迭代里，模型要做的工作并不一样：读资料、核对参数、整理证据、编写实现，也要分析失败路径、判断系统边界、决定修复方案。把每一步都交给最贵的模型，意味着常规工作也在按顶级推理能力付费。

我们用 **GPT-6 Astra + Qwen-3.8 Flash** 跑了一组工程研究任务。在两组达到相同整单验收标准的配对中，HiRoute 混合模式的 **API 等价成本分别降低 92.01% 和 91.39%**。关键决策环节，混合模式和全 Astra 均为 **3/3 无重大错误**，全 Qwen 为 **1/3**。

这里“同等质量”指达到同一预先规定的交付验收标准，不是每条回答、每项评分完全相同。90% 指本文研究案例中的 API 等价成本降幅，包含路由决策与受试调用开销；不是订阅账单或所有任务的通用降幅。全部轮次和评分口径见[实验记录](../experiments/cases/research-cost-quality/README.md)。

## 一段工作，不需要一种固定的模型能力

真实工程工作的能力需求会变化。同一份调研中，大量内容是在已有资料里寻找明确答案，少量内容却需要组合多个系统的行为，推导原文没有直接写出的结论。代码迭代同样如此：清晰、局部的修改与涉及并发、兼容性和失败恢复的判断，需要不同的投入。

| 工作阶段 | 常见工作 | 适合的模型分工思路 |
| --- | --- | --- |
| 调研与准备 | 核对文档、整理参数、建立证据清单 | 明确的来源内工作优先考虑经济模型 |
| 设计与决策 | 分析约束冲突、事务边界、故障顺序 | 将更强模型留给复杂推理 |
| 实现与验证 | 局部修改、运行检查、分析失败 | 根据具体任务及已观察到的表现选择 |
| 长程推进 | 多轮工具调用、压缩上下文、继续修复 | 阶段内保持稳定，在交接点重新评估 |

这是一种分工原则，不是给每个生命周期阶段永久贴上“简单”或“复杂”的标签。实现阶段也可能需要强推理，研究阶段也包含大量明确工作。

HiRoute 把这种选择放到路由层。任务分解仍由工作流或 Agent 完成；本实验预先定义了交付单元，由 HiRoute 与官方 Jev 扩展选择每个单元实际使用的模型。

## 实验一：360 条研究资料，加一个真正需要推理的决策

任务模拟一次消息系统架构评审的准备工作，覆盖 RabbitMQ、Kafka、NATS、Pulsar、Redis Streams 和 RocketMQ。每个系统有 60 个不同的核验项，共 360 条；每条都要给出判断、事实解释和来源行号。

接下来还要完成一份 Kafka 与 SQL 协作的事务语义备忘录：分析给定方案的安全性、活性、故障窗口，以及修复建议能否兑现要求。

这个任务需要大量工作量，但没有要求模型凑字数。资料部分限制为直接回答核验项，关键决策部分保持简洁。真正考验强模型的是推理密度，而不是输出长度。

我们比较三种模式：

- **全 Astra**：所有交付单元使用 Astra。
- **HiRoute 混合**：相同任务进入智能路由；实际记录显示六份资料整理使用 Qwen，关键备忘录使用 Astra。
- **全 Qwen**：相同交付要求，固定使用 Qwen。

混合组的 Jev 判断规则是通用的：来源中明确存在的抽取、翻译、核验和整理工作可考虑经济模型；需要推导新保证、处理矛盾或分析复杂失败交互的工作交给主力模型。规则没有使用产品名称或隐藏参考答案指定模型。完整冻结资料提供给受试模型，Jev 看到当前任务、核验项和来源元数据。

## 便宜在哪里，质量守在哪里

两组通过原定整单验收的配对结果如下。验收要求是完整交付 360 条，其中至少 353 条正确，且关键备忘录无重大错误。

| 配对 | HiRoute 混合资料核验 | 全 Astra 资料核验 | 混合关键决策 / Astra 关键决策 | 保守成本降幅 |
| --- | --- | --- | --- | --- |
| 第 2 组 | 357/360 | 359/360 | 通过 / 通过 | **92.01%** |
| 第 3 组 | 356/360 | 359/360 | 通过 / 通过 | **91.39%** |

成本按全部受试尝试及 Jev 决策核算，使用冻结的 API 价格和汇率。保守降幅用混合组成本上界除以全 Astra 成本下界计算。上表展示通过原定验收的两组，三个配对的完整结果均保留在实验记录中。

质量差异最值得关注的是关键建议。在三次完整备忘录审查中：

| 模式 | 关键决策无重大错误 |
| --- | --- |
| HiRoute 混合 | **3/3** |
| 全 Astra | **3/3** |
| 全 Qwen | **1/3** |

全 Qwen 的两次问题并非 JSON 格式错误。它在某些修复建议里，把 SQL 状态与偏移的本地事务绑定，或 outbox 方案，作为 SQL 与独立 Kafka 输出跨系统原子可见性的解决方案。这些手段有各自适用的价值，但仅靠它们不能消除题设要求下的跨系统可见性窗口。

这解释了混合路由的价值：大量资料工作可以使用经济模型，而少数影响方案可靠性的关键判断值得投入更强推理。全 Qwen 的资料整理准确率本身接近混合组；差距出现在决策环节。

## 长任务自动模型接力：不用一直盯着换模型

一次选对模型还不够。长任务会持续调用工具、遇到失败、修复实现，并在上下文变长后压缩历史。最初合适的模型，未必始终适合后续工作。

HiRoute 的**长任务自动模型接力**利用这些自然交接机会：

1. 普通工具续轮保持已有路由，避免每次调用都重新选择。
2. 消息历史经过压缩等操作而无法继续继承时，重新进入决策。
3. Jev 结合当前任务和可见的历史执行表现，选择后续分支，并可给出此前阶段的胜任度评分。
4. 本次评分低于配置下限时，阻止继续选择经济分支，由主力模型接续。

底层由 ContextHold 判断上下文连续性。它不要求客户端额外报告“发生了压缩”，也不意味着每次压缩必然换模。评分是路由参考，最终质量仍由任务验收确定。不同模型不能共享 KV cache；交接后建立新前缀，随后继续复用。

## 实验二：一次指令，约 32 分钟，343 项验收通过

为了验证自动接力，我们另选了一个固定版本的 HTTPX 软件修改任务：增加同步与异步 JSON 流式迭代，正确处理 JSON、NDJSON、JSON text sequence、编码和流消费状态，并确保能在剩余数据到达前产出已解析的值。

这次使用原生 Agent 执行代码和工具，而不是只提交一次文本请求。任务同时要求实现和验证，运行中不允许人工追加指导或修改产品代码。

![长任务记录：Qwen 开始执行，上下文交接后 Astra 接续，最终通过 343 项独立验收](assets/unattended-handoff-zh.svg)

| 观察项 | 实际结果 |
| --- | --- |
| 初始任务指令 | 1 条 |
| 中途人工提示 / 人工代码补丁 | **0 / 0** |
| 原生任务运行时间 | **31 分 36 秒** |
| 实际模型请求 | Qwen 25 次，Astra 15 次 |
| 第二次压缩后的升级 | 阶段胜任度 **0.485**，低于 **0.5** 下限 |
| 升级后的实际操作 | 13 次 Astra 工具调用 |
| 独立验收 | **108 项功能 + 229 项回归 + 6 项增量性断言，全部通过** |

验收在执行结束后独立进行，原有受保护测试保持不变。这个案例展示了实际发生的自动升级和完成结果；它没有全 Astra 成本对照，因此不用于宣称节省 90%。[任务、参数与验证方法](../experiments/cases/unattended-engineering/README.md)

## 在自己的工作流中开始

先接入 Astra 和 Qwen，再建立智能省钱计划：将 Qwen 放在经济分支，将 Astra 放在主力分支。需要结合复杂度与执行表现选路时，可配置[官方 Jev 扩展](../decision-extensions/extensions/jev-decider/README.zh-CN.md)。

本文研究案例使用简单任务阈值 0.8、胜任度下限 0.5。长任务案例为了观察自主升级，单独使用经济模型优先的阈值 0、胜任度下限 0.5。两个策略服务不同实验目的；不要将它们混为一套通用最优参数。

连接惯用 Agent 后，在 HiRoute 会话记录中核对实际执行模型、路由决策和用量。不要仅凭模型配置名称判断路由已经生效。

从 [HiRoute 安装入口](https://hiroute.ai/download/)开始，或者先离线重算本文结果：

```sh
python3 experiments/reproduce.py verify
python3 experiments/reproduce.py report
```

[experiments/](../experiments/README.md)包含完整交付、逐条缺陷记录、成本来源、任务和重跑入口。离线核算不调用模型；在线重跑使用自己的接入配置，结果单独保存。语义审查仍需逐条阅读，不能把结构检查当作质量评分。

这些数据来自有目的设计的案例，每组仅三次重复，评估未盲化，代表的是本案例的观察结果。完整原验收结果、补充评估与传输恢复记录均公开在实验目录中。

把模型能力投入最需要它的工作，让常规工作用更经济的方式推进，让长任务在需要时自动接力——这是 HiRoute 希望带来的工作方式。
