# HiRoute repository invariants

- Use current Issue/Design decisions, repository durable specs, code and executable tests as authority. Requirements must be self-contained. Resolve consequential conflicts before affected implementation, while continuing unrelated work.
- Start from the [code map](docs/code-map/README.md) to find the production owner and a representative scenario. Update affected map entries and local guides when responsibilities, entry points or contract boundaries change; keep detailed requirements in their owning specs.
- For user-facing workflow changes, new user guides and release preparation, follow [website documentation maintenance](apps/website/README.md#documentation-maintenance). Update affected bilingual instructions, Agent/CLI handoffs and product screenshots with the change; complete the revision-bound documentation review before a new release is published.
- For user-facing critical paths, limit synchronous work to the dependencies needed to complete the operation, and verify that unrelated state growth does not add heavyweight work.
- For resource optimizations, preserve valid production-request serviceability first, then minimize HiRoute memory use without excessive added foreground latency. Internal memory accounting targets must not become rejection limits for required request state.
- Follow [agent instruction ownership](.agents/README.md) when changing instructions or skills. Claude uses repository skills exposed through `.claude/skills/` and must not load Codex-only skills through indirect references.
- Before writing GitHub Issues, PRs or attachments, read and follow `rules` and `guidance.shared` in `issue-spec/config.yaml`. Keep process records in the corresponding Issue/PR and raw evidence in ignored artifacts.
- Before every authorized public push, including validation pushes, use [public PR checks](.agents/skills/hiroute-public-pr/SKILL.md) on the complete outgoing history. Human review and merge remain the default.
- For selecting, executing or diagnosing checks and preparing validation handoff, use [HiRoute validation](.agents/skills/hiroute-validation/SKILL.md). Select scope by changed behavior and affected consumers. Bind results to the actual tested revision; missing required cases or fixture-only success cannot establish product completion.
- Keep each checkout's default `target/`; share compiler objects only through sccache. Never use external Cargo targets or `cargo clean`, and never clean active runs. Preserve source worktrees and unique evidence during owner-led cleanup.
- For persisted data, configuration, recovery, published CLI/Gateway behavior, OS filesystem/process boundaries or release handoff, use [compatibility maintenance](.agents/skills/hiroute-compatibility/SKILL.md). Keep one current contract per boundary; register intentional legacy support in [the compatibility register](contracts/compatibility-support.v1.json).
- For Desktop/Web interaction consistency, controls, wording, form/confirmation states, layout or visual hierarchy, use [interaction and UI quality](.agents/skills/hiroute-ui-quality/SKILL.md), with analogous production flows, affected states and source-bound before/after evidence.
- For concrete issue-spec CLI or workflow friction encountered during work, use [workflow improvement](.agents/skills/hiroute-workflow-improvement/SKILL.md). File deduplicated, labeled suggestions in the owning repository for later analysis, and assess adopted improvements when a later relevant task has sufficient context; this authorizes feedback collection, not automatic implementation or workflow rewrites. Honor narrower user instructions.
